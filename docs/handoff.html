AZ TOUCH

Build a real, playable, XDJ-AZ-inspired standalone-screen experience using a custom VirtualDJ skin. The touchscreen is the player display; the FLX10 is the physical mixer and decks. Rekordbox-exported USBs are the primary music source.

0. Instructions to the AI coding agent

You are the implementation agent. Build and ship an installable, working solution, not a design-only prototype. Read this entire brief first. Perform the feasibility and USB import gates before investing in visual polish. Then implement a VirtualDJ skin and any strictly necessary, documented configuration/mapping assets. Continue iteratively until tested on the target computer or clearly blocked by missing physical access, software licensing or an SDK limitation.

Project working title: AZ Touch. It is an independent XDJ-AZ-inspired interface; it is not actual AlphaTheta firmware, and it must not claim affiliation with AlphaTheta, Pioneer DJ, rekordbox or Kiwi Gazza. The user owns a Surface Pro 7 touchscreen and a Pioneer DJ DDJ-FLX10. They already know rekordbox but dislike its desktop look. They want the experience of a standalone four-deck XDJ-AZ screen while mixing through their FLX10.

Technical decision: Use VirtualDJ’s supported skin engine and FLX10 driver/mapping first. Do not build a new audio engine, use Electron to fake a DJ screen, reverse-engineer firmware, or attempt unsupported process-memory hooks. An optional helper or supported plugin is permissible only after documenting a specific missing capability, confirming a documented public API, and getting approval.

Success looks like: the user launches VirtualDJ, activates the AZ Touch skin, connects the FLX10 and an existing rekordbox USB, opens Source → OneLibrary, selects a rekordbox playlist and loads tracks onto all four decks. The screen immediately reflects real deck state (audio, positions, cues, elapsed/remaining, BPM and key), the browser works by touch and FLX10 navigation, and closing/reopening the app preserves settings. All functionality must be live rather than static decoration.

No clarification needed before starting. If the agent has no access to the Surface, make the XML skin, documented tests and installation scripts and clearly label hardware tests “NOT RUN”; do not claim they passed. Request hardware access only when necessary for validation.

Touchy AZ: inspect before implementing

Creator’s 2026 Touchy discussion. Kiwi Gazza describes a display-only skin with AZ four-deck, two-deck, CDJ, and hybrid variants, including an exact-fit 3:2 Surface layout. Noteworthy ideas: no redundant jog/mixer UI; a safe playing-waveform needle lock; per-deck identity; large performance data; a shared browser and playlist shortcuts; optional FX X-PAD. The first catalogue submission was declined, and a public release is not verified here. Do not assume the skin can be downloaded or reuse its code/assets without authorisation.

Style hierarchy

Prioritise authentic player feel: dark nearly black canvas, square high-contrast cells, strict consistent spacing, restrained blue navigation highlights, bright deck colours, full-width horizontal waveforms, small technical labels, high-visibility time/BPM/key, embedded overall-waveform preview, hot-cue labels and persistent four-deck strips. It should look like DJ equipment, not a Windows program skinned with generic cards.

This is a release-blocking feature.

4. Exact interface and UX specification

4.1 Screen and scaling

  • Target Microsoft Surface Pro 7: 12.3 inch; 2736 × 1824 physical pixels; 3:2 aspect; 10-point touch. Windows display scaling and effective rendering pixels must be detected instead of hard-coded assumptions.
  • Primary skin design coordinate system: 1368 × 912 (3:2) or a validated alternative exact-fit 3:2 canvas. The agent must validate the engine’s handling of Windows scaling. No distorted circles, clipped browser, black padding or non-touchable offset regions.
  • Landscape, fullscreen/kiosk-like stage performance. Keep an unobtrusive and easy Settings/Exit path. Optional mouse and keyboard remain supported.
  • Critical touch buttons should have comfortable physical touch targets, aiming for about 9 mm or larger where practical; adapt to actual rendered DPI. Browser row heights should be larger than stock desktop VirtualDJ where feasible.
  • Skin should remain usable at 150%, 175%, 200% Windows UI scaling if the engine respects those options; document tested combinations.

4.2 Global visual shell and modes

  • A slim top navigation band: SOURCE · BROWSE · TAG LIST · PLAYLIST · SEARCH · WAVEFORM · FX · SETTINGS. Touch must visibly change mode; button state remains synchronised with currently shown panel.
  • At all times, show the selected source, USB presence/disconnect state, currently playing deck(s), loaded deck track names, and a working path to return to Waveform. The browsing modes preserve a four-deck status strip.
  • Startup mode: Waveform four-deck view, with an optional last-used mode setting. No modal splash or marketing UI.
  • Panels must use stable screen coordinates and the VirtualDJ skin-panel mechanism (or equivalent SDK-supported constructs). The official skin must remain configurable.

4.3 Waveform / performance

  • Four live logical decks numbered 1, 2, 3, 4. Do not mistakenly assign channels based only on left-to-right physical FLX10 placement; see deck mapping contract below.
  • Provide two accessible modes: 4 DECK (four stacked real scrolling waveforms) and 2 DECK (two larger waveforms for current primary decks; four small lower status strips remain visible). Deck pair toggle 1+2 and 3+4 is optional only after base mode works.
  • For each deck: large track title, artist if available, deck label, current BPM, original BPM where feasible, pitch %, harmonic key, remaining/elapsed switch, master/sync/quantize/loop states, on-air signal if SDK supports it, loaded and playing states, cue labels, and overall track progress.
  • Waveforms must be backed by real VirtualDJ deck renderers. Use SDK waveform objects (e.g. scratchwave/rhythmzone/songpos) as verified; do not draw static sine bars in the actual product.
  • Moving waveforms are non-interactive while audio is playing by default (“needle lock”). If paused, safe seeking can be enabled only using supported VDJScript/SDK behaviour and after physical touchscreen testing; provide a persistent setting to turn touch seeking off altogether.
  • Hot cues A–H should reflect imported rekordbox cue state when available and be visibly distinct by deck. If labels/colours cannot be imported, use correct existence/position with fallback markers and document discrepancies.
  • Do not duplicate full-size jogs, faders or mixer EQs on screen. The primary physical mixer is the FLX10.

4.4 Browse

  • Native live browser, not an in-memory imitation: physical USB folders, rekordbox/OneLibrary playlists if exposed by VirtualDJ, hierarchical navigation, scroll, sorting and search. Build with native browser or split browser elements rather than recreating VirtualDJ databases.
  • Prominent left-side Source/playlist navigator and large track table. Aim for name, preview waveform where supported, artwork where supported, BPM, key, length, artist, rating/colour optionally. Do not promise waveform preview per browser row until SDK element supports it.
  • Touch actions: tap row to select (not start playback), double-tap or explicit LOAD to load into chosen deck, swipe/drag to scroll, Back to parent, search keyboard opens reliably, persistent source/playlist breadcrumbs.
  • Dedicated deck load buttons for decks 1–4 in browser mode. The FLX10 hardware LOAD/BROWSE actions must still work and must not be remapped blindly.
  • Prevent accidental loading over an actively playing deck. Use a loading guard appropriate to VirtualDJ, visually show “deck playing / load locked” and test user override. Never silently interrupt a playing track.
  • Provide a pre-listen workflow only if Native VDJ browser prelisten route can be wired to actual FLX10 headphones. First test routing and whether touch preview is available; otherwise label preview as unsupported rather than inventing a functional-looking button.

4.5 Source, playlist, tag list, search

  • Source page differentiates local storage, actual attached rekordbox USB, native VirtualDJ folders, and local rekordbox library (if present). A USB source with playlists must be usable without copying every file into a new laptop collection.
  • Playlist mode is a navigation shortcut into folders/plists exposed by the VDJ library, not a duplicate proprietary library browser. Treat changes to drive contents as non-destructive unless explicitly requested.
  • Tag List uses VDJ’s documented playlist/sidelist or suitable built-in list, with clear labelling that functionality is analogous, not necessarily interoperable with a Pioneer hardware Tag List.
  • Search filters the current source and/or global library using documented VDJ browser search controls; Windows touch keyboard usability is required.

4.6 FX, cues and extras

  • FX overlay (optional v1 extension after core) matches native VDJ effect states for target deck/master, effect name, time/beat division, on/off, wet/dry level and optional touch X-PAD if supported.
  • Do not present sliders or preset choices that are not wired to real VirtualDJ functions. Hardware FLX10 FX state remains the source of truth, not a shadow fake state.
  • Hot-cue rows may optionally be touch-triggerable only after deck loading and needle-lock are safe. Keep FLX10 performance pads fully functional.
  • Keep Slip, Quantize, Key Sync, Beat Jump, Loop and PFL visible only where the SDK can expose actual states/actions reliably. Every optional function requires a positive test.
  • Offer an “Emergency return to Waveform” action from every page; standard navigation should never seize focus from FLX10 audio processing.

5. Architecture / technical constraints

LAYER 1

VirtualDJ engine

Live audio engine, cue/grid analysis, four-deck playback, headphone routing, effects, rekordbox/OneLibrary browsing as supported.

LAYER 2

AZ Touch skin

XML skin and PNG assets: deck rendering, native browser sections, state-aware labels, touch actions, mode panels and 3:2 layout.

LAYER 3

FLX10 controller

Official VirtualDJ device definition, MIDI mapping, jog screens, four-deck layer switching, audio I/O, channel FX, sampler/stems.

5.1 Supported skin SDK

VirtualDJ official Skin SDK describes distributable .zip skins containing a .xml skin definition and graphics .png, optional preview/assets. Start by extracting the shipped/default skin from VirtualDJ Settings → Interface, studying real working XML and modifying a copy rather than inventing arbitrary XML tags. Validate required elements directly against the official Browser, Custom Browser, Scratchwave, Deck and VDJScript verbs docs.

Use one skin archive named AZ-Touch-3x2.zip. Its internals must follow the version of the official SDK actually installed; at a minimum include a verified .xml, background sprite atlas .png and preview .png if supported. Copy into the user’s VirtualDJ Skins directory as documented, then select in Settings → Interface. Include a simple uninstall/restore-default option. Avoid editing VirtualDJ program binaries or redefining MIDI controllers where the factory mapping already works.

5.2 Browser SDK boundaries

The official SDK offers a monolithic <browser> and modular elements including <folderlist>, <fileview>, <filelist>, <browsertoolbar>, <browserinfo> and <prelisten>. Prefer native elements. Exact per-row artwork/waveform visuals may not be skin-customisable beyond the browser’s own supported columns; the agent must investigate and either implement a proven approach or document an honest approximation.

Switch page panels using verified skin_panel/skin_panelgroup actions. Bind every deck widget under the correct <deck deck="1"> ... </deck> context or an equivalent tested deck targeting method. Position data should be centralised, with a generated XML skin if that reduces manual mistakes. Check the VirtualDJ skin XML before installing.

6. Build phases — execute in this order

P0 — Environment and backups (first)

Actions: Record Windows version, Surface CPU/RAM, VirtualDJ build, installed audio driver, FLX10 firmware/mapping, display scaling, sample rate and audio device. Back up VirtualDJ settings/mappings/library metadata. Obtain or make clone of a rekordbox USB. Record whether OneLibrary only or OneLibrary + legacy Device Library was exported.

Exit: “Environment Facts” table with all versions, backup paths and licence status. Do not proceed with paid/unlicensed controller use or production USB modifications.

P1 — Prove FLX10 audio and USB import

Actions: In stock VirtualDJ UI, choose the FLX10 native audio preset, test master/headphone cues and four physical decks. Insert test USB, locate playlists under OneLibrary and/or drive paths, play real tracks from USB, compare hot cues, grids and metadata to rekordbox on at least 10 tracks. Test unplug and reinsert while not playing; separately test guarded behaviour for disconnect during a playing set using duplicate media only.

Exit: G0–G3 matrix with screenshots. If OneLibrary fails, isolate whether the issue is absent OneLibrary library, missing old-format dual export, VirtualDJ version, incompatible filesystem, or a reader limitation. Do not fake passing import by showing plain audio files.

P2 — Skin spike

Actions: Create working minimal .zip skin at 1368 × 912. Render distinct labels for decks 1 and 2, one actually moving waveform, a browser list with a real USB source, visible Settings, a Waveform ↔ Browse toggle and one touch load action. Install/reload in VirtualDJ and confirm touch coordinates match visuals.

Exit: A valid installable skin and screenshots/videos proving four exact capabilities. XML syntax must match official SDK, not unvalidated generated text.

P3 — Four-deck core view

Actions: Build four live waveform rows, track metadata, main cue indicators, 2-deck/4-deck modes, colours, play/paused indicators, elapsed/remaining and resilient unloaded-state placeholders. Add a paused-only waveform seek guard if technically supported; otherwise disable seeking and document.

Exit: Four simultaneously loaded and optionally playing tracks display correct deck-specific movement and values on Surface at native display resolution. Hardware level/jog/pad changes are reflected without stalling audio.

P4 — Browse + source modes

Actions: Native browser with accessible left folder tree, larger touch track rows, search, scrolling, browse encoder interoperability, source selection, playlist shortcuts and safe Load 1–4. Preserve a four-deck status strip at the bottom. Avoid incorrectly showing unsupported imported metadata or preview waveforms.

Exit: User can navigate a verified rekordbox USB's playlists by touch, load all decks and return to Waveform in no more than one navigation tap.

P5 — FLX10 mapping validation

Actions: Test native mapper first. Verify deck layer selectors left 1↔3 and right 2↔4, all cue/load buttons, jog displays, CUE/PLAY, BPM/pitch adjustment, Beat FX section, pads, track separation, main outputs, headphone PFL. Only change mappings when they are proven conflicting with AZ Touch; save original and document every custom mapping.

Exit: Four-deck audio unaffected by page changes; hardware controls remain logically consistent on both deck layers.

P6 — Safe advanced features

Actions: Implement and test optional touch FX panel, hot cues, quantize/loop/Slip indicators, touch preview, tag/sidelist behaviour and sensible hot-cue labels, in that order. Only features supported by verified VDJScript/SDK functionality may be exposed. If effects can't be mirrored to screen truthfully, hide them.

Exit: Every visible interactive advanced control is wired, observable, and documented; no placeholders masquerade as actual effects.

P7 — UI polish and performance

Actions: Tighten spacing/palette, tune waveform redraw speed/CPU use and touch target size, eliminate mouse-only controls in core workflow, test screen scaling/fullscreen and long track names. Perform 60-minute playback endurance test and a 4-deck stress scenario with USB in use; watch for audio pops/dropouts, frozen UI and missing database data.

Exit: Smooth real-time audio and clear readability; all critical test cases pass or are explicitly blocked with evidence.

P8 — Package and hand off

Actions: Build deterministic skin ZIP, provide installation and rollback scripts, screenshot gallery, source licence/credit note, USB compatibility report, test results and documented known limitations. Record actual version tested, checksums and exact files changed. Explain required VirtualDJ licence and avoid distributing VirtualDJ itself.

Exit: Install ZIP through VirtualDJ/Skins directory and select it, with clear rollback instructions. No hidden runtime that depends on an AI coding environment.

7. Binding / interaction contracts

7.1 Deck state contract (agent-maintained ledger)

Create a manifest mapping each displayed property/action to its verified official SDK or VDJScript implementation. For each row store source, action/expression, unit, false/empty behaviour and proof screenshot. Required properties: loaded state, title/artist, remaining time, elapsed time, BPM and pitch, harmonic key, waveform, song progress, cue markers, play/pause, deck number and quantize. Optional: original BPM, FX selected name/target/on/off, on-air, stems and track preview. If no stable SDK method exists for a property, omit it from the released UI instead of guessing.

7.2 FLX10 deck assignment

The FLX10 left physical deck side selects VDJ deck 1 or 3; right side selects VDJ deck 2 or 4 with the physical DECK SELECT controls. In the four-channel mixer, never equate deck side with all channel fader positions. Verify hardware mixer channels 1–4 against VirtualDJ output routes and perform an audible test on each.

7.4 Sound safety rules

  • Changes to browsing modes, skin appearance or screen orientation must never change audio output, channel fader position, effects activation or deck transport state.
  • Loading a selected track to an already playing deck must require a documented safety guard and deliberate override; prefer a non-playing target by default if appropriate.
  • Set touch hit testing so a gesture cannot inadvertently scratch, nudge, jump cue or drag the playback needle mid-set.
  • If a USB is removed unexpectedly, show a clear error, preserve other working decks, avoid automatic rescans that disturb live playback, and recover gracefully upon reconnection. Test using cloned media.
  • Do not depend on localhost web apps, browser extensions or automatic cloud services for core playback. USB and local playback must work offline if supported by the host.

Performance budget

Aim for visibly smooth waveform updates at the actual hardware rendering capability and glitch-free audio at realistic buffer settings. Record CPU utilisation with 2 and 4 decks, memory, VirtualDJ's audio performance meters (where available), startup time, and browse response. Do not assert an unmeasured FPS or latency value. Render graphic assets efficiently, avoid unnecessary stacked transparent layers, and prefer native VDJ waveforms over manually redrawing waveform raster every frame.

9. Final deliverables / definition of done

  1. AZ-Touch-3x2.zip — real installable VirtualDJ skin compatible with tested version.
  2. README.md — one-page quick install, activation, starting VirtualDJ with FLX10, navigating USBs and switching modes.
  3. Compatibility report — exact rekordbox export types read successfully and cue/beatgrid results, plus what requires dual-format export.
  4. Mapping/action registry — every action and displayed property with verified SDK syntax and test evidence.
  5. Install and rollback scripts — never overwrite user settings without backups and explicit consent.
  6. Real screenshots — Waveform 4-deck, 2-deck, Browse on USB, Source, FX if implemented, at Surface native 3:2.
  7. Test report — T01 through T20, with blocked/not-run clearly shown. Include release hash and tested VirtualDJ version.
  8. Known limitations — clear explanation of unsupported library metadata, partial AZ parity and features not yet available.

Final acceptance: This must behave like a standalone player display. A user should be able to leave the Surface keyboard folded away, plug in a rekordbox USB, navigate playlists, load and DJ on their FLX10, and see genuine live four-deck data on a deliberately designed 3:2 touchscreen. Functionality is more important than perfect visual resemblance. Never fake OneLibrary compatibility, working effects, waveforms or tests.

If engineering is blocked

Return a short blocker report with: the command/action tried, current state, screenshot/log, which requirement cannot be met, the official SDK limitation, whether a supported VirtualDJ plugin could solve it and what permissions it would require. Ask for a specific required decision (e.g., authorise the licence, allow dual-format USB export, provide physical Surface access) rather than proposing an entirely new app as the first response. A native independent DJ app is only a last-resort alternative because it would entail audio, MIDI, beatgrid, waveform, database, driver and USB-format engineering far beyond the objective.
